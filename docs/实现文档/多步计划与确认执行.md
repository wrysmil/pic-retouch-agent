## 2. 提交 2：计划结构与图

### 2.1 `backend/app/agent/plan.py`（新增）

纯数据结构 + 状态机，不碰数据库，便于单测。

- `assemble(raw)`：补 `id`（缺省 `s{序号}`）、补 `depends_on`（缺省串到上一步）、补 `status`（缺省 `pending`），并做三项拒绝——超过 `MAX_STEPS = 8`、依赖悬空、依赖成环。成环用 Kahn 拓扑排序判定：`incoming` 计数消不完即仍有环。
- `validate(raw)`：逐步过 `spec_of` 与 `tool_service.validate`，再交给 `assemble`。工具存在性与参数合法性因此和界面点击完全同源。
- `ready(steps)`：`status ∈ {pending, waiting}` 且尚无 `run_id`，且所有依赖 `succeeded`、无依赖落入 `{failed, canceled}`。
- `settle(steps)`：汇总整轮。仍有开跑/待跑的一律 `running`，除非**只剩 `waiting`**（没有任何 `queued`/`running`）才回 `queued`；随后依次判 `failed`、`canceled`，全绿为 `succeeded`。
- `needs_confirm(steps)`：`len(steps) > 1`。单步不多一次点击。
- `cancel_remaining(steps)`：只把 `pending`/`waiting` 标 `canceled`，正在跑的不打断。

### 2.2 `backend/app/agent/graph.py`

- 删掉 `AgentDeps` 与 `dispatch` 节点：图不再持有数据库会话，也不再下发工具，`run(goal, context)` 去掉 `deps` 形参。
- `_verify` 改为调用 `plan.validate`，捕获 `UnknownTool / InvalidParams / PlanError` 三类，统一回「这一步暂时执行不了：{原因}」并清空计划。
- 系统提示词放开多步：「可以一次安排多步，按完成先后调用；后一步默认依赖前一步」「能一步完成的不要拆成多步，最多 8 步」。

`__init__.py` 相应只导出 `run` 与 `PlannerUnavailable`。

## 3. 提交 3：执行循环与接口

### 3.1 `backend/app/services/agent.py`

`respond()` 不再驱动图执行，改为按 `plan_mod.needs_confirm` 决定落库状态：

| 情形 | `AgentRun.status` | `reply` |
|---|---|---|
| 规划异常 | `failed` | 空，错误进 `error` |
| 多步计划 | `queued` | 缺省补「将按以下步骤执行，确认后开始。」 |
| 单步计划 | `running` | 立即 `_advance` |
| 无计划（闲聊/拒绝） | `succeeded` | 模型正文 |

核心是 `_advance(session, turn)`：

```python
while progressed:
    for step in plan_mod.ready(steps):
        if spec_of(step["tool"]).needs_approval and not step.get("approved"):
            step["status"] = plan_mod.WAITING      # 花钱的工具不擅自跑
            continue
        run = await tools.submit(...)              # 画布工具当场跑完
        step["run_id"], step["status"] = str(run.id), run.status.value
        await session.commit()                     # 每落一步提交一次
        progressed = run.status is RunStatus.SUCCEEDED
```

- `progressed` 只在「当场成功」时为真，因此画布链会一口气推完，像素链会停在 `queued` 等 worker。
- 循环结束后再 `settle` 一次；若因 `waiting` 停在 `queued`，补一句「下一步需要确认后再执行。」

四个入口：

- `confirm`：`waiting → pending` 并打上 `approved`，整轮转 `running` 后 `_advance`。
- `cancel`：`cancel_remaining` + `_cancel_queued_runs`，后者把仍是 `queued` 的 `ToolRun` 用 `runs.finish(status=CANCELED, error="已取消")` 结掉，避免 worker 之后取出执行。
- `retry`：倒序找最后一个 `failed` 步骤，清空 `run_id` 置回 `pending`，重新 `_advance`。
- `continue_plan(run)`：worker/当场执行完成后的回调，按 `run_id` 反查所属轮次，同步该步状态后 `_advance`。

两个实现细节：

1. **JSONB 原地改不会被 ORM 察觉**。所有写回都走 `_copy(turn.plan)` 得到新列表再整体赋值，并额外 `flag_modified(turn, "plan")`。
2. **推进不能自触发递归**。`tools.submit` 内部对画布工具会同步走到 `execute → continue_plan`，此时本轮计划里**还没有**这一步的 `run_id`（赋值发生在 `submit` 返回之后），`_turn_of_run` 反查不到，天然断链。

### 3.2 `backend/app/services/tools.py`

`execute()` 末尾追加 `agent_service.continue_plan(session, run)`。用函数内局部导入：`services/agent` 模块级要 `from app.services import tools`，反向导入会成环。

### 3.3 `backend/app/schemas/agent.py`

`PlanStepOut` 补 `id` / `depends_on` / `status`。`status` 对老数据兜底：有 `run_id` 视作 `succeeded`，否则 `pending`，避免历史对话回填时步骤显示成「等待中」。

### 3.4 `backend/app/routers/sessions.py`

新增 `POST /sessions/{id}/messages/{turn_id}/{confirm,cancel,retry}`，异常到 HTTP 的映射统一：`TurnNotFound → 404`，`Cannot{Confirm,Cancel,Retry} → 409`。

## 4. 提交 4：对话区

- `api/agent.ts`：`PlanStep` 补 `id`/`depends_on`/`status`，新增 `StepStatus` 联合类型与三个动作方法。

## 6. 已知限制

- `_turn_of_run` 只在最近 20 轮里找，超出一轮长计划跨越 20 轮新对话的极端情况不再推进。
- 无依赖关系的步骤仍按 `ready` 顺序串行下发，未做并行。
- 计划推进依赖 `ToolRun` 完成回调，用户直接在界面点工具（不属于任何计划）不会触发推进，这是预期行为。
