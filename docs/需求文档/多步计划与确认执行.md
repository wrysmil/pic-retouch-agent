# 需求文档：多步计划、依赖执行与确认重试

> 项目：pic-retouch-agent（AI 修图智能体）
> 主题：Agent 一轮指令从「单步下发」升级为「多步计划 + 确认 + 断点续跑」
> 日期：2026-10-12
> 前置：S11（拆层成层、图层单独操作）

## 1. 背景与目标

S11 之前，一轮自然语言指令最多规划成一步，图里规划完就当场下发，工具跑完这一轮就结束了。三个问题随之而来：

1. **一句话只能改一件事**。「去背景再调亮一点」「先拆层再换背景」这种复合诉求，模型只能挑一个工具做，剩下的靠用户再补一句。每补一句都要重新描述上下文。
2. **花钱的操作没人过问**。规划完立刻下发，多步里只要有一步要调生成模型，用户看不到总共要做几件事、要花多少次调用，只能事后撤销。
3. **进度是断的**。步骤状态只活在 HTTP 请求期间，页面一刷新、worker 一重启，这轮计划做到哪儿了就没人知道了。

本里程碑把「规划」和「执行」拆开：图只产出并校验计划，计划落库后才按依赖逐步推进，步骤状态写回同一份计划里。

## 2. 用户与场景

| 角色 | 场景 |
|---|---|
| 创作者 | 输入「去背景再水平翻转」，看到两步计划列出来，点「执行计划」才开始跑 |
| 创作者 | 计划里第一步在排队，第二步显示「等待中」，第一步完成后第二步自动接着跑 |
| 创作者 | 中途点「取消后续」，没开跑的步骤变「已取消」，正在跑的那一步不受影响 |
| 创作者 | 某一步失败（模型超时），修复后点「重试失败步骤」，只重跑这一步 |
| 创作者 | 计划跑到一半刷新页面，回来仍是原进度，不会整轮重跑 |
| 创作者 | 计划进行中输入框锁住，提示先确认或取消，避免两条计划互相踩画布 |

## 3. 功能需求

### 3.1 计划结构 F1

- **F1.1** 一轮指令最多规划 **8 步**，超出直接拒绝，并要求用户拆成多次说明。
- **F1.2** 每步有稳定标识 `id`（缺省按顺序补 `s1`、`s2`……）、工具名、参数、`depends_on` 依赖列表、`run_id` 与 `status`。
- **F1.3** 模型未显式给出依赖时，按给出顺序**串成链**：后一步默认依赖前一步。
- **F1.4** 依赖指向不存在的步骤、或依赖图成环时，整轮计划作废并给出中文原因。
- **F1.5** 步骤状态取 `pending` / `waiting` / `queued` / `running` / `succeeded` / `failed` / `canceled` 七种之一；整轮状态由各步状态汇总得出。

### 3.2 校验 F2

- **F2.1** 模型给出的工具名与参数一律服务端校验，与界面点击共用同一套入参模型，不允许「界面能过、模型调用过不了」。
- **F2.2** 校验失败（工具不存在、参数非法、结构非法）时整轮计划清空，回一句中文说明，不下发任何工具。
- **F2.3** 图内不再有「下发」节点：规划与校验完成即结束，执行由服务层按计划驱动。

### 3.3 确认与执行 F3

- **F3.1** 单步计划直接开跑；**多步计划先停在 `queued`**，等用户确认。
- **F3.2** 标记为需要批准的工具（`needs_approval`）在未获批准前置为 `waiting`，等用户确认后才下发。
- **F3.3** 确认接口放行所有 `waiting` 步骤并继续推进；没有可确认步骤时返回 409。
- **F3.4** 取消接口把 `pending`/`waiting` 的步骤标为 `canceled`，并把还排在队列里的工具任务结掉，防止 worker 之后执行已取消的步骤；已在执行或已结束的轮次返回 409。
- **F3.5** 重试接口只重建**最后一个失败步骤**的工具任务，已成功步骤不重复执行；无失败步骤返回 409。
- **F3.6** 三个接口对不存在的轮次统一返回 404。

### 3.4 依赖执行与断点续跑 F4

- **F4.1** 一步结束后推进计划：把该步状态写回计划，再下发所有「依赖全部成功」的步骤。
- **F4.2** 画布类工具当场成功，同一次推进里连续带出后续步骤；像素类工具入队后整轮停在 `running`，等 worker 回调继续。
- **F4.3** 每落一步就提交一次，计划即断点。刷新页面或 worker 重启后按库里的步骤状态继续，不整轮重跑。
- **F4.4** 依赖失败的步骤不再尝试下发，整轮按汇总状态收尾。

### 3.5 对话区界面 F5

- **F5.1** 步骤卡片显示序号、工具中文名与当前状态；正在跑的步骤显示进度百分比与阶段文案。
- **F5.2** 轮次处于 `queued` 时给出「执行计划」「取消」两个按钮；`running` 时给「取消后续」；`failed` 时给「重试失败步骤」。
- **F5.3** 有轮次处于 `queued`/`running` 时锁住输入框，并把占位文案换成说明为什么要锁。
- **F5.4** 空对话的引导文案改为复合指令示例，提示多步计划会先列出再执行。

## 4. 非功能需求

- **NFR1** 计划推进不得引入递归下发：同一次 `submit` 内不得再次触发本轮计划的推进。
- **NFR2** 不新增数据库表与列。步骤状态存在 `agent_runs.plan` 这个 JSONB 里，改动须被 ORM 感知。
- **NFR3** 单步指令的交互成本不增加：不确认、不点击，行为与本里程碑之前一致。
- **NFR4** 计划推进失败不得污染工具自身的执行结果；工具已成功即记成功。

## 5. 验收标准

- [ ] 两步计划下发后 `status=queued`，两步 `run_id` 均为空，画布文档未变。
- [ ] 确认后两步依次执行，`flip_layer` + `rotate_layer` 的结果同时体现在图层变换上。
- [ ] `remove_background` + `flip_layer`：确认后第一步拿到 `run_id`、第二步为空；worker 跑完第一步后第二步自动执行，整轮 `succeeded`。
- [ ] 取消后两步均为 `canceled`，画布未变。
- [ ] 无选区调用 `replace_region` 失败后，重试产生新的 `run_id`，整轮回到 `running`。
- [ ] 环状依赖与超过 8 步的计划分别被拒绝。
- [ ] 单步生成指令的轮次状态为 `running`，工具跑完后为 `succeeded`。

## 6. 范围与非范围

**在范围内**：计划结构与状态机、服务端校验、确认/取消/重试三个接口、按计划推进的执行循环、对话区步骤卡片与按钮。

**不在范围内**：计划模板与历史复用、跨轮次的依赖、并行下发无依赖的步骤（当前一律按依赖串行）、把计划暴露为可编辑结构。

## 7. 后续依赖

- 后续「图层、选区按层拆步」要把画布摘要里的图层与选区信息细化到步级，依赖本里程碑的计划结构。
- 后续「批量像素处理」复用同一套排队与进度回调，不重复实现推进逻辑。
