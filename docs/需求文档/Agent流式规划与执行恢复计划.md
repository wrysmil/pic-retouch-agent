# Agent 流式规划与执行恢复计划

> 日期：2026-10-21
> 状态：规划草案，尚未实施。
> 对应方向：合并「Agent 规划过程流式输出」与「LangGraph checkpoint 持久化」。
> 核对依据：当前仓库源码；截图作为需求线索，其中对现状和实现方式的描述已重新核对。

## 1. 目标与完成后的体验

用户发送修图指令后，立即看到这一轮已创建，随后看到规划阶段、逐步出现的候选步骤，最后得到经过服务端校验的正式计划。多步计划仍需用户确认，单步沿用现有执行规则。

刷新页面能恢复本轮规划或执行状态；服务进程重启后，可以从可靠记录继续推进。已完成的图片处理不重复执行，外部调用结果不确定时明确提示核查，不自动再次调用付费服务。

这里的流式反馈是公开的操作摘要和计划草稿，例如「正在安排去背景与尺寸适配」。不要求模型输出内部思维链，也不把阶段提示包装成模型的真实思考过程。

## 2. 当前实现与实际缺口

| 范围 | 源码现状 | 本次需要补齐 |
|---|---|---|
| 规划图 | `backend/app/agent/graph.py` 只有 `plan → verify`；通过 `ainvoke()` 等待完整工具调用 | 流式获取规划片段；对外转换为稳定的业务事件 |
| HTTP 请求 | `services/agent.py::respond()` 等模型返回后才创建 `AgentRun` | 先创建轮次并返回，再由后台运行规划；断开浏览器不终止任务 |
| 计划与历史 | `AgentRun.plan` 已用 JSONB 保存步骤、状态与 run_id | 保留既有回填能力，补恢复扫描和并发控制 |
| 步骤执行 | `services/agent.py` 推进计划，`services/tools.py` 与 ARQ 执行工具；执行发生在图外 | 图 checkpoint 与业务执行分别定义恢复边界 |
| 进度推送 | `/events/runs/{run_id}` 已提供工具 SSE，Redis Pub/Sub 转发并先发快照 | 增加轮次级事件、规划草稿快照和断线补齐 |
| 前端 | `useAgent.ts` 获取历史，最新轮次 running 时约 800ms 轮询 | 订阅轮次事件，历史快照恢复，轮询降为兜底 |
| 重试 | 已有 confirm/cancel/retry 和失败步骤重试 | 补任务孤立、执行结果未知、重复投递与状态不一致的处理 |
| 依赖 | `backend/pyproject.toml` 的 agent 可选依赖已声明 `langgraph-checkpoint-postgres` | 核对实际安装版本、驱动、连接池与部署安装方式 |

因此，不能把本项目描述为「刷新就会丢失所有执行进度」。更准确的缺口是：规划阶段尚未提前落库，现有业务状态的异常恢复尚未形成完整闭环。

## 3. 方案取舍

| 方案 | 优点 | 局限 | 结论 |
|---|---|---|---|
| 只完善现有 JSONB 状态机 | 改动较小，可直接改善重启恢复 | 没有图级状态历史和规划节点恢复 | 可作为过渡，但不覆盖完整目标 |
| 规划图持久化 + 业务执行状态机恢复 | 复用现有工具与队列，图和执行各有清晰边界 | 需要显式关联 checkpoint、轮次、步骤和工具任务 | **推荐** |
| 将规划、确认和所有执行迁入 LangGraph | 可以统一工作流表达 | 涉及 ARQ、确认接口、同步工具、画布修改的大幅迁移 | 本期不做，后续另行评估 |

本期 checkpoint 覆盖规划图节点，不宣称它会自动恢复图外图片执行。整轮恢复由 checkpoint、业务任务账本和恢复协调器共同完成。

## 4. 数据与职责边界

### 4.1 轮次先落库

新增独立 `phase` 字段表达 `planning / awaiting_confirmation / executing / completed / failed / canceled / needs_attention`，避免复用现有 `queued` 同时表示待确认与真实排队。

- `AgentRun` 保存轮次所有者、会话、输入修订号、规划上下文快照、模型配置版本、phase、规划尝试号、公开草稿与错误信息。
- 消息提交增加用户级幂等键。同键同内容返回原轮次，同键不同内容返回冲突；重复点击不再多建任务。
- 新增正规化步骤记录 `AgentStep`：轮次、稳定 step_id、顺序、工具参数、依赖、审批、状态、当前工具任务、输入/输出修订号。`(turn_id, step_id)` 唯一。
- `ToolRun` 增加可空的步骤关联和 attempt 编号；一次重试创建新 attempt，保留旧任务记录。
- 逐步将 `AgentRun.plan` 改为兼容投影；新轮次的步骤状态以 `AgentStep` 为准，不双向修改两份事实源。旧轮次回填后再启用新调度。
- 将当前「扫描最近 20 条对话反查工具任务」替换为明确的步骤关联，长会话也能可靠续跑。

用户可见轮次快照由业务表生成；图 checkpoint 只供内部恢复与诊断。客户端不直接读取或提交任意 checkpoint_id。

### 4.2 可持久化的图状态

当前 `AgentState` 含 `ChatOpenAI` 客户端对象，接入 saver 前必须移出。图状态只放可序列化的数据：轮次 ID、规划尝试、目标、固定上下文、配置版本引用、工具草稿、校验后计划和公开摘要。

模型客户端、数据库连接、事件 writer 通过运行时依赖注入，不进入 checkpoint；不保存密钥、连接对象或图片字节。已有配置版本固定规则继续生效，恢复不切换到新发布模型。

### 4.3 Postgres saver 生命周期

- 在 API/worker 各自生命周期创建并关闭异步 saver/连接池，按实际安装版本使用 `AsyncPostgresSaver`。
- 数据库已经使用 asyncpg，不代表 saver 可以直接复用 SQLAlchemy 连接；核对并安装 saver 所需的 psycopg 依赖和正确 DSN。
- 首次建表由受控初始化命令执行一次，不在每次请求调用 setup。
- `thread_id` 按 `turn_id + planning_attempt` 生成，保持短且稳定；用数据库映射校验用户和会话归属。
- 规划异常恢复使用同一 thread；用户明确重新规划才创建新 attempt。单个未完成 LLM 节点可能需要重新调用，无法恢复厂商已生成但未持久化的半段 token。
- 评估节点同步持久化模式；以实际锁定版本的 API 为准。阶段提交与恢复测试通过前，不默认采用只在退出时保存的模式。
- checkpoint 与业务表不假设处于同一事务；通过确定性的 `turn_id/attempt`、校验后计划摘要和幂等写回消除跨提交窗口。
- 默认建议完成轮次 checkpoint 保留 30 天，可配置；会话删除触发映射、checkpoint 和事件清理。

## 5. 流式协议与前端交互

### 5.1 提交、订阅、恢复

拟调整 `POST /api/sessions/{session_id}/messages`：快速创建轮次并返回 `202 + turn_id + phase`，通过事务 outbox 投递 `plan_agent_turn`，不在 HTTP 请求内等待模型。与现有前端同步升级，短期保留旧返回字段作为兼容投影。

新增：

- `GET /api/sessions/{session_id}/messages/{turn_id}`：当前轮次快照。
- `GET /events/agent-runs/{turn_id}`：轮次 SSE，沿用现有登录机制和独立代理配置。
- `POST /api/sessions/{session_id}/messages/{turn_id}/resume`：仅用于已经分类、允许恢复的状态；自动扫描与此接口共用协调器。

现有历史、确认、取消、重试和工具 SSE 接口继续服务原有流程。读取历史仍能恢复待确认计划；不会因为重新打开页面自动批准计划。

### 5.2 业务事件

统一信封包含 `event_id / seq / turn_id / planning_attempt / type / timestamp / payload`。

| 事件 | 内容 | 前端行为 |
|---|---|---|
| `turn.snapshot` | phase、公开摘要、草稿、正式计划、步骤状态、last_seq | 首次连接和刷新重建界面 |
| `planning.started` | 开始时间与阶段描述 | 立即显示正在规划 |
| `planning.summary.delta` | 模型明确提供的公开说明片段，可选 | 追加简短说明；没有正文也正常工作 |
| `planning.step.draft` | call_index、稳定草稿 ID、工具标签、部分可读参数 | 逐步显示灰色草稿卡，标记尚未校验 |
| `plan.ready` | 已校验完整计划与计划版本 | 一次性替换草稿，按规则显示确认按钮 |
| `planning.failed` | 用户可读错误、是否可重试 | 停止等待，保留输入 |
| `step.updated / turn.updated` | 已落库的业务状态 | 更新步骤和整轮阶段 |

规划器当前以 tool_calls 为主，且提示词要求不输出解释。首期以工具调用片段形成逐步出现的计划草稿，不增加一次「先生成长段解释」的额外调用。真正的公开说明可选支持，不成为流式功能的前置条件。

工具参数片段按 call_index 聚合；容忍任意网络分块和不完整 JSON。只有完整工具调用经过原有参数、依赖、最多 8 步校验后，才生成正式计划。草稿无执行权限，校验失败时撤回草稿并说明原因。

模型不支持工具调用流式输出时，降级为真实阶段事件 + 最终完整计划，不能模拟逐字推理。联调时覆盖正文为空、仅工具参数流、正文与工具交错三种输出。

### 5.3 持久事件与断线补齐

- 增加 `AgentEvent`，轮次内 seq 唯一；公开摘要 delta 可按 50–100ms 合并，避免每个 token 一次数据库事务。
- 状态变更与关键事件在同一业务事务提交，outbox 在提交后发布 Redis 通知；Redis 只负责唤醒，不作为恢复事实源。
- 支持 `Last-Event-ID` 或显式游标。先建立通知订阅，再读快照/事件；客户端按 seq 去重，缺口从数据库补齐。
- 事件保留期结束时发送完整 snapshot 与新的游标，不能让客户端无限请求已经删除的历史。
- 断流采用退避重连；持续失败时轮询快照。关闭页面只关闭订阅，不取消任务。
- 文本支持减少动态效果设置，中文组合输入、长计划滚动和键盘确认保持可用。

## 6. 执行恢复与防重复

### 6.1 先处理现有事务窗口

目前 `runs.create()` 自行 commit，`tools.submit()` 随后入队，再由 `_advance()` 写回计划里的 run_id。存在「任务已创建甚至开始执行，但尚未关联步骤」的窗口；队列去重不能覆盖这个数据库窗口。

将服务方法改为支持调用方控制事务。步骤锁定、ToolRun 创建、关联与 outbox 写入原子提交；提交后单独投递。同步画布工具也先建立关联，再执行，避免执行完成回调找不到所属步骤。

### 6.2 恢复分类

| 检查结果 | 恢复动作 |
|---|---|
| 规划已完成但业务计划未写回 | 用同一 attempt 的已校验结果幂等写回 |
| 步骤已有成功 ToolRun，整轮未推进 | 对齐步骤终态，推进下一个依赖，不重跑成功步骤 |
| 已创建任务但未入队 | outbox 重投原 run_id |
| 已入队、未开始 | 保留排队，确认队列状态后补投 |
| 本地确定性处理租约失效 | 在确认旧执行者失效后重新领取原逻辑步骤 |
| 外部请求已发送但结果未知 | 进入 needs_attention；有厂商任务 ID 则先查询，禁止盲目重发 |
| 外部成功、资产已保存，画布未应用 | 幂等补应用和终态，不再次调用模型 |
| 待用户确认或已取消 | 保持原状态，不自动放行 |

恢复协调器在 worker 启动时及周期扫描运行，使用租约与数据库抢占，避免每个 API 实例同时扫描推进。建议初始 30 秒扫描、15 秒心跳、90 秒租约失效判定，均配置化，并结合实际耗时校准。

### 6.3 一致性约束

- 每个逻辑步骤最多一个有效执行租约；通过条件更新/行锁领取，完成写入检查租约代数，旧 worker 不能覆盖新状态。
- 画布应用记录以 run_id 唯一，资产产物用 run_id + output_index 唯一，恢复不重复生成历史或加入图片墙。
- 外部调用记录独立 attempt、请求幂等键、厂商请求/任务 ID、发送状态与结果；厂商不支持幂等与查询时明确保留未知状态。
- 同一会话的画布修改串行化。确认执行时校验基准 revision；之后每步按上一步输出 revision 继续。用户在待确认期间修改画布则提示重新规划，不能静默覆盖。
- 前置步骤失败时，下游明确进入 blocked/skipped，不保留为永远无法推进的 pending；重试前置步骤后按依赖规则恢复下游。整轮可结束为失败，不因残留等待项一直显示 running。
- 取消只阻止未开始步骤，运行中的外部请求按现有能力处理；迟到结果可以保存，但不越过 revision 检查修改画布。
- 与免费额度计划共用预占和结算键；恢复原任务不重复预占，结果未知时不擅自释放额度后再次调用。

## 7. 分阶段交付

| 阶段 | 工作范围 | 可独立验收的结果 |
|---|---|---|
| A1：先建轮次与流式规划 | 轮次 phase、消息幂等、后台规划、事件表/outbox、SSE、前端草稿与快照；先接入现有执行器 | 用户立即得到反馈、逐步看到计划，刷新不丢本轮输入与规划状态 |
| A2：规划图 checkpoint | 运行依赖移出 state、异步 saver、初始化/清理、规划结果幂等回填 | 规划图持久化可查询，重启后恢复可恢复节点 |
| A3：步骤账本与执行恢复 | 步骤正规化、事务提交、租约/心跳、恢复扫描、画布幂等应用、未知结果分类 | 执行中重启可继续已确认任务，成功步骤和画布应用不重复 |
| A4：灰度与兼容收口 | 旧计划回填、配置开关、真实模型与真实断进程演练、监控 | 新旧会话可用，异常可观测，可关闭新入口而不遗失已创建任务 |

首个用户可体验版本为 A1；只有 A3、A4 验收后才宣称「端到端断点恢复」。

## 9. 验收与观测

1. 无真实模型调用的前提下，消息创建与首个阶段反馈目标为正常开发环境 p95 ≤ 1 秒；真实首个模型片段耗时单独统计，不能用固定动画掩盖。
2. 使用可控分块桩覆盖半截 JSON、多工具交错、非法参数、无工具流；非法草稿从不触发 ToolRun。
3. 规划中、待确认、工具运行中分别刷新；重复订阅和重复提交不产生重复轮次或步骤。
4. 在任务创建未投递、投递未开始、外部返回、资产保存、画布应用、步骤结束未推进等边界强制终止进程，逐项核对恢复结果。
5. 重复确认、双 worker 抢占、取消与完成竞态、旧租约迟到写入均不产生重复应用或扣减。
6. 跨用户访问事件、轮次、恢复接口均被拒绝；checkpoint 和日志不含密钥。
7. 已成功步骤保留，结果未知任务不自动再次调用；恢复后仍使用原配置版本。
8. 记录消息提交延迟、首阶段/首模型片段耗时、规划耗时、重连数、恢复成功率、租约超时、未知结果数、checkpoint 写入失败。日志能按 turn/step/run/attempt 关联。

本轮仅审阅源码和编写计划，以上均为实施验收项，尚未执行。

## 10. 上线与待确认项

采用新增字段/表、旧轮次回填、新轮次开关、灰度启用的顺序。回退时停止接收新流式轮次，已经创建的轮次继续由兼容协调器处理；不能卸载迁移后让任务无人接管。

实施前确认：实际 LangGraph 版本与 saver 驱动；线上反向代理 SSE 配置；真实模型工具调用流式支持；外部图片厂商是否支持幂等键/任务查询。首版保留「单步直接执行，多步确认」规则。
