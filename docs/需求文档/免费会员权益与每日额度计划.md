# 免费会员权益与每日额度计划

> 日期：2026-10-21
> 状态：规划草案，尚未实施。
> 对应方向：会员权益与使用次数管理。
> 已确认边界：当前所有用户均为免费会员；每天固定免费次数；暂不接入 VIP、充值或购买；前端 VIP 可以展示为「即将开放」。

## 1. 本期目标

每个用户都能看到自己是免费会员、今天还可使用多少次，以及哪些功能会消耗次数。达到上限后明确显示下一次重置时间，保留已生成素材、基础编辑和下载能力。

后台统一设置每日免费次数；后端覆盖直接生成、编辑页工具、Agent、批量和后续营销任务，不能依靠前端按钮禁用控制额度。

本期不创建支付订单、不接支付 SDK、不提供充值入口、不发放 VIP 权益，也不提供管理员将用户升级为 VIP 的操作。预留会员类型的扩展结构即可，无需先建设交易系统。

## 2. 当前基础与缺口

| 现状 | 本期用途 |
|---|---|
| `models/user.py` 已有角色、启停状态、认证版本 | 继续用于账号管理；管理员角色与会员权益分开 |
| `services/tools.py::submit()` 是界面与 Agent 的工具提交入口 | 统一授权和预占的主要入口 |
| `services/generation.py`、`tools/enhance.py`、`tools/marketing.py`、`services/batch.py` 会调用图片服务 | 必须覆盖所有外部图片调用，不仅限制文生图接口 |
| `AgentRun / ToolRun` 已固定模型配置版本 | 额度规则也固定版本，任务恢复不突然改变消耗规则 |
| 后台已有用户管理、配置发布与审计 | 增加免费权益配置、额度查询和有理由的纠错操作 |
| 当前源码未见会员额度、额度流水与支付实现 | 新增免费权益和账本；不把已有任务次数统计当作余额 |

此前的后台/模型规划文档不能代表现在的实施状态，本计划以当前源码为准；已有管理功能直接扩展，避免重复建设后台。

## 3. 会员展示与功能权益

### 3.1 当前仅生效免费会员

| 内容 | 当前行为 |
|---|---|
| 会员身份 | 所有用户显示「免费会员」，管理员使用工作台同样适用额度规则 |
| 基础工具 | 裁剪、旋转、翻转、普通调色、图层调整、已有素材下载可用，不消耗 AI 免费次数；保留通用频率与资源限制 |
| AI 图片能力 | 消耗每日次数；功能自身的模型可用性、参数限制照常检查 |
| 每日上限 | 后台统一配置 N 次，正式数值待确定；开发示例可用 5，不能视为已确认生产值 |
| VIP 展示 | 「VIP 会员 · 即将开放」，说明后续将开放更多权益；不显示已生效价格、购买按钮或付款码 |
| 用尽额度 | 提示「今日免费次数已用完，明日 00:00 重置」，展示准确本地时间；不引导到不可用的支付流程 |

规划、历史查询、状态订阅、ZIP 下载不计入 AI 图片次数。LLM 规划虽然不扣图片次数，也要有独立频率、并发和输入长度限制，防止无限规划消耗。

去背景、拆层、OCR 等当前可能是本地处理的功能按真实执行方式分类，不因按钮标有 AI 就直接扣次数；它们可设独立频率/批量上限。超分或后续模型策略变化后，也须重新确认是否实际调用外部服务。

### 3.2 次数的建议口径

建议按「成功交付的一张 AI 图片」计 1 次，而不是一次点击或一整个批次。

| 场景 | 建议计算 |
|---|---|
| 生成 1 张图片 | 预占 1，成功保存且可访问后结算 1 |
| 一次生成 4 张候选图 | 预占 4；实际成功交付 3 张则结算 3、释放 1 |
| 一次 AI 图片编辑输出 1 张 | 1 次 |
| 仅完整留白适配到 3 个尺寸 | 0 次，无外部 AI 调用 |
| 对 3 个目标分别做 AI 扩图 | 最多 3 次，提交前展示 |
| 2 张素材，每张先换背景再 AI 扩图 | 最多 4 次，按实际 AI 处理单元结算 |
| 本地模板排版、改文案后重新导出 | 0 次；额外生成背景再按产出结算 |
| Agent 规划为 3 步，其中只有 1 步需要 AI 图片 | 按该步输出张数计，不因步骤多扣次数 |
| 用户重复下载或刷新查看结果 | 0 次 |

以上是可配置规则的推荐初稿，实施前确认是否接受按张计数。UI 使用「次数」但必须同步解释「每成功生成或 AI 处理 1 张消耗 1 次」。多步操作的中间图片若已保存且可在历史/素材中访问，也算该步成功交付，后续步骤失败不撤销其消耗；仅厂商内部不可访问的中间态不算。额度不足时不能悄悄把生成 4 张改成 1 张。

## 4. 额度规则与每日重置

- 时区固定为 `Asia/Shanghai`，自然日 00:00 切换。数据库保存 UTC 时间，按权益配置时区计算 quota_date 与 reset_at，不读取宿主机本地时区。
- 使用按日额度桶，无需每天批量把所有用户清零；首次使用当天额度时创建该日桶。
- `available = limit + adjustment - reserved - consumed`，余额查询与扣减使用同一口径。
- 桶创建时复制规则版本和上限。后台发布新上限默认从下一自然日生效；当天紧急修正通过有原因的调整流水完成，不直接覆盖已消耗数字。
- 待确认计划只给消耗预估，不长时间占用额度；用户确认时重新校验并预占。单步直接执行在提交时预占。
- 跨午夜任务归属预占时的日期，完成后结算原桶；仍有有效预占的自动重试/恢复沿用原归属，不从新一天重复扣次。原预占已释放后由用户再次重试，按重试当天日桶重新预占，并记录同一逻辑单元的新预占代数；次日发起的新操作也使用新日桶。
- 预占有生命周期，但已发送外部请求的预占不能单凭超时自动释放；先核对执行状态。

## 5. 数据模型与责任边界

首期可新增以下表，不在 users 上只加一个可随意覆盖的「剩余次数」。

| 模型 | 主要字段与约束 |
|---|---|
| `MembershipPolicyVersion` | 不可变规则版本、member_type=free、日上限、计数单位、能力限制、时区、生效日期、发布人 |
| `QuotaBucket` | user_id、quota_date、policy_version、limit、adjustment、reserved、consumed；用户+日期唯一 |
| `QuotaReservation` | 用户、桶、业务根任务、AI 处理单元、预计数量、已结算/已释放数量、状态；逻辑处理单元唯一 |
| `QuotaLedger` | 不可变流水，reserve/consume/release/adjust、数量、关联任务/预占、操作人、原因、幂等键 |
| `ImageCallAttempt` | 工具/步骤/item、逻辑处理单元、厂商请求 ID、发送状态、输出资产、失败/未知原因、attempt |

用户身份当前始终解析为 free；可在响应模型预留 membership_type 字段，首期不保存可生效的 VIP 套餐和到期时间。角色 admin 不自动得到无限次数，测试账户通过 mock 与开发配置隔离。

`ImageCallAttempt` 与恢复计划中的外部调用 attempt 共用一套结构，不能各建一份无法对账的调用记录。会员额度是产品权益；厂商 Token、实际调用成本和失败重试次数是另一种统计口径，不能混为一张余额表。

## 6. 统一校验、预占与结算

### 6.1 提交前算清消耗

扩展工具规格或新增消费规则注册表，使每个工具能按已校验参数计算 `consumption_units`，区分 local、AI 单图、多张候选、批量/多目标复合任务。

批量与 Agent 计划先展开为稳定的逻辑 AI 单元。价格/次数不能由浏览器或 LLM 自报；后端根据工具、数量和操作链计算。父任务预占覆盖子单元，子工具领取同一预占额度，避免父子各扣一次。

直接生图、工具按钮、自然语言、批处理都必须调用统一权益服务；外部图片调用边界再次验证有效 reservation，以覆盖复合工具内部直接调用 provider 的现有路径。

### 6.2 并发安全

一次业务事务完成：幂等请求检查、日桶条件更新、预占和流水创建、任务创建、逻辑单元关联、outbox 投递记录。提交后才发布队列任务。

目前 `runs.create()` 自行提交，需要与恢复计划协调改为可组合事务；不能先让外部调用开始，再扣余额。采用数据库条件更新或行锁保证 available 足够，不能使用「读出剩余次数，Python 减一再覆盖」。

网络重试、同请求重复点击、ARQ 重投、Agent 恢复，均复用原预占键；只有用户明确发起新操作才新建逻辑消费单元。原预占释放后的显式重试创建新的预占代数，旧代数的迟到回调不能结算新预占。

### 6.3 状态与异常口径

| 结果 | 用户额度处理 | 外部成本记录 |
|---|---|---|
| 参数/权限/模型不可用，未发送 | 不预占或全额释放 | 记录拦截原因，无真实调用 |
| 排队后取消，尚未发送 | 释放对应数量 | 无真实调用 |
| 成功生成、保存且可访问 | 结算成功交付数，释放缺少部分 | 记录真实调用和产出 |
| 厂商明确失败，无可交付结果 | 释放 | 失败调用仍保留 |
| 厂商成功，但下载/存储失败 | 优先重试取回/保存原结果；明确无法交付后释放 | 原调用成本和失败阶段保留 |
| 超时或进程中断，厂商结果未知 | 暂保留预占，进入核查；有任务 ID 先查询 | 标记 unknown，不当作零成本 |
| 成功结果重复回调或任务恢复 | 根据幂等键返回已结算结果 | 不新增虚假的业务消费 |

自动重试次数和频率有上限；重新下载原结果不重复消耗。需要重新调用厂商时，记新的成本 attempt，但同一逻辑处理单元最终成功只消耗约定次数。已经释放的失败任务若由用户重新尝试，须重新预占并关联原任务；不能无额度重试。

未知预占超过建议 15 分钟进入待人工核查列表，按厂商最长任务时长配置。后台支持有理由地结算或释放；释放后到达的旧结果只留审计，不得未经授权透支新一天额度或自动覆盖画布。

## 7. 前后端功能

### 7.1 用户端

- 账号菜单/个人面板：免费会员、每日总量、已用、处理中预占、可用次数、下次重置时间。
- 生图与 AI 操作提交前：显示「预计使用 X 次，当前可用 Y 次」；数量或参数变化后重新估算。
- 计划卡片：在确认按钮旁显示整份计划预计次数；恢复只显示尚未结算部分，避免把成功步骤重复计算。
- 批量与营销：按素材×目标×AI 操作解释消耗，可展开明细；本地适配和模板导出显示不消耗次数。
- 用尽：保持输入和编辑状态，允许降低数量后重新提交，显示重置时间；新一天重新获取权益后恢复入口。
- VIP：展示只读「即将开放」区域，无购买或升级按钮，不能出现模拟成功弹窗。
- 失败/取消后重新获取权益，多个标签页靠服务端快照同步；前端展示延迟不能影响后端真实判定。

### 7.2 后台

- 免费权益配置：每日上限、并发/频率限制、生效日期、版本历史与发布确认。
- 用户详情：当天 limit/reserved/consumed/available，按日查看流水，关联任务与异常预占。
- 纠错：额度调整、释放异常预占，要求原因，记录操作者；不支持任意改余额而不留流水。
- 总览：活跃用户、额度用尽人数、预占异常数、成功交付图片数、免费使用分布。厂商成本统计若未建设，不在此阶段假装已有精确成本。

### 7.3 建议接口

| 接口 | 内容 |
|---|---|
| `GET /api/me/entitlements` | free 身份、能力、日桶、规则版本、重置时间、VIP coming_soon |
| `POST /api/quota/estimate` | 校验任务意图后计算预估，不预占；正式提交重新校验 |
| `GET /api/me/quota-ledger` | 分页展示自己的额度流水 |
| `GET/POST /api/admin/membership-policies` | 免费策略查询与发布 |
| `GET /api/admin/users/{id}/quota` | 用户额度和异常预占 |
| `POST /api/admin/users/{id}/quota-adjustments` | 有原因、可审计的额度纠错 |

约定业务错误 `QUOTA_EXHAUSTED`（409）、`FEATURE_UNAVAILABLE`（403）、`RATE_LIMITED`（429）。响应含可用次数、所需次数、reset_at 和用户文案；不要返回「余额不足请充值」。

前端 `api/client.ts` 目前主要提取错误文本，需要兼容结构化错误与旧 detail 字符串；通过错误 code 呈现耗尽状态，不匹配中文字符串做逻辑判断。

## 8. 分阶段交付

| 阶段 | 工作 | 用户可见结果与验收 |
|---|---|---|
| C1：免费身份与权益展示 | 策略版本、权益接口、账号额度区域、VIP 即将开放、后台每日上限 | 所有用户显示免费身份；无任何可用 VIP、支付、充值入口 |
| C2：统一额度闭环 | 日桶、预占/流水、任务事务、所有图片入口校验、成功/失败结算 | 单图、多张、Agent、批量均真实受限，并发不超用 |
| C3：跨日与异常恢复 | unknown 核查、幂等回调、恢复任务关联、调整审计、管理列表 | 刷新/重启/跨午夜/部分失败不重复扣减，可追查每笔次数 |
| C4：灰度启用 | shadow 估算、mock 演练、真实调用核对、配置发布、存量任务收口 | 按用户灰度限制，核对账本后正式启用；用尽不会破坏基础编辑和下载 |

C1 可以提前用于界面验证，但在 C2 完成之前不能对外宣称每日额度已经生效。真实图片服务的额度限制应在上线开放前完成。

## 9. 验收标准

1. 所有现有账号和新账号均解析为免费会员，普通用户不能自行提高次数，管理员工作台也没有隐式豁免。
2. 日额度为 N 时，同时提交超过 N 个单位，最终成功预占数不超过 N；重复请求不多占。
3. 从所有入口验证相同规则，尤其是 batch 内部直接调用 provider、Agent 重试和营销多目标任务。
4. 生成 4 张成功 3 张，仅消耗 3；确定失败/未发送取消释放；结果未知保留并可核查。
5. 23:59 预占、次日完成仍结算原桶；次日新任务使用新桶，刷新显示正确重置时间。
6. 外部成功后存储异常，恢复保存不重扣；重复回调、双 worker、恢复扫描竞态不造成负余额。
7. 今日额度用尽仍可裁剪、调色、访问既有素材和下载；规划接口仍受独立限流约束。
8. 发布新策略、管理员调整、异常释放都有流水；账本能与 bucket 的 reserved/consumed 对账。
9. VIP 展示只含即将开放；页面、接口、后台都无法完成充值、购买或升级。
10. mock 联调与真实调用分别核对；模拟消耗不污染生产用户额度与真实厂商统计。

本轮未实现、迁移数据库或运行这些验收。测试重点为数据库事务、并发和恢复边界，不能只测试前端按钮灰显。

## 10. 上线策略与待确认参数

先增加表和接口，再在 shadow 模式计算而不限制，对比真实调用链确认无遗漏；最后按用户灰度启用强制预占。开关关闭时仍完成已存在 reservation 的结算，不能直接删除账本。存量已发送任务标记为启用前任务，不追扣旧额度；新提交任务必须使用新策略。

实施前只需确定以下业务数值：

- 每日免费总次数 N（截图的 5 次仅为示例）。
- 是否接受「每成功交付一张 AI 图片计 1 次」；推荐接受，以免一次批量绕过日限额。
- 同时运行任务上限、规划频率和本地重计算上限。
- 管理员当日纠错权限和调整上限。

本期明确不做：VIP 开通/到期、套餐定价、支付、充值、订单、退款、自动续费。未来若决定开放 VIP，再单独设计，不能把预留字段当作已接入会员。

建议协作顺序：先与 [Agent 流式规划与执行恢复](Agent流式规划与执行恢复计划.md) 共用任务幂等、outbox 与外部调用 attempt，再给 [智能尺寸适配与营销模板](智能尺寸适配与营销模板计划.md) 增加 AI 单元估算和预占。三个计划可分期交付，共享的事务基础只实现一套。
