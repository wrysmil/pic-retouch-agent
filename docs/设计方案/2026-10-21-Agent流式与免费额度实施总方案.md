# Agent 流式与免费额度实施总方案

> 日期：2026-10-21
> 依据：[Agent 流式规划与执行恢复计划](../需求文档/Agent流式规划与执行恢复计划.md)、[免费会员权益与每日额度计划](../需求文档/免费会员权益与每日额度计划.md)
> 状态：实施中。本文只记录本次实际落地的设计取舍、数据结构、接口与阶段验收，不重复需求文档的背景论证。

## 0. 总体策略

两个需求共享三块基础能力，先建一次，两边复用：

1. **可控事务边界**：`runs.create()` 不再自行 commit；任务落库、额度预占、步骤关联、事件写入由调用方一次提交，提交成功后才投递队列。
2. **幂等键**：消息提交用「用户 + request_id」，额度预占用「逻辑消费单元键」，队列任务继续用 `run_id` 作 `_job_id`。
3. **事件与 outbox**：业务状态变更与事件同事务落 `agent_events`；提交后用 Redis 仅做唤醒，数据库是恢复事实源。

执行顺序：**C1 → C2 → A1 → A2 → A3 → C3 → A4/C4 收口**。
先做 C1/C2 的原因：额度是纯增量域，依赖少、可独立验收，同时会把 `submit()` 的事务边界改造成 A1/A3 需要的形态。

## 1. 共同基础

### 1.1 事务边界

改造后 `services/tools.submit()`：

```
校验参数
→ 解析并锁定 runtime_config_version_id
→ runs.create(..., commit=False)   # flush 拿 run.id
→ quota.reserve(..., run_id=run.id) # 同一事务条件更新日桶
→ session.commit()
→ 入队（仅 commit 之后）
→ 画布类工具 execute()
```

`execute()` 结束时先写额度结算/释放，再由 `runs.finish()` 与任务终态一起提交。队列重投、worker 重启读取到终态任务时直接返回，不重复结算。

### 1.2 幂等

| 场景 | 键 | 行为 |
|---|---|---|
| 发送修图指令 | `(user_id, request_id)` | 同键同文本返回原轮次；同键不同文本 409 |
| 工具提交 / 重试 | `(user_id, logical_key)`，默认 `run:<run_id>` | 已存在且未释放则直接返回，不重复预占 |
| 队列投递 | `run_id` | ARQ `_job_id` 天然去重 |
| 事件写入 | `(turn_id, seq)` | 唯一约束，重放幂等 |

### 1.3 外部调用的结果口径

`ImageCallAttempt` 首期建表，记录 `not_sent / sent / succeeded / failed / unknown`。
厂商请求已发出但进程中断时，任务进入 `needs_attention`，预占保留，不自动重发付费调用。
首期不对接厂商任务查询的适配器；没有任务 ID 时由后台人工核对。

## 2. 免费额度域（C1/C2/C3）

### 2.1 计数规则

- 单位：**成功交付且可访问的 1 张 AI 图片 = 1 次**。
- 本地处理不计次：裁剪、旋转、翻转、图层调整、普通调色、去背景（rembg）、投放尺寸留白、模板排版、导出、下载。
- 调外部图片模型的工具计次：`generate_image`、`replace_background`、`expand_canvas`、`upscale_image`、`replace_region`、`erase_region`、`generate_marketing`、`split_layers`、`promote_object_to_layer`。
- 计次数量由后端按已校验参数计算，不接受前端或模型自报：

| 工具 | 预占次数 |
|---|---|
| `generate_image` | `count` |
| `replace_background` | `count` |
| `generate_marketing` | `count` |
| `expand_canvas` / `upscale_image` / 局部编辑 / 拆层 / 提升图层 | 1 |
| `batch_process` | 逐素材展开操作链：每个外部模型操作产生 1 个 AI 单元；本地操作不增加 |
| 其余画布/本地工具 | 0 |

- 实际结算取 `min(预占, 成功交付张数)`；不足部分释放。失败/未发送取消全额释放；结果未知保留并进入核查。
- 多步计划确认前只展示预估，确认时重新校验并预占；单步计划在提交时预占。

### 2.2 日桶与策略

- 时区固定 `Asia/Shanghai`，自然日 00:00 切换；数据库存 UTC，`quota_date` 按策略时区计算。
- `available = limit + adjustment - reserved - consumed`。
- `MembershipPolicyVersion` 不可变；发布新版本默认 `effective_from = 明日`，当天不变。日桶创建时复制规则版本和上限。
- 首次使用当天额度时创建日桶，不做每日批量清零。
- 新版本同日紧急修正走 `QuotaLedger` 的 `adjust`，不直接改已消耗数字。

### 2.3 数据表

- `membership_policy_versions`：member_type、version_seq、daily_limit、counting_unit、timezone、features、effective_from、published_by、note。
- `quota_buckets`：user_id、quota_date、policy_version_id、limit、adjustment、reserved、consumed；`(user_id, quota_date)` 唯一。
- `quota_reservations`：user_id、bucket_id、policy_version_id、logical_key、units、settled、released、status、run_id、turn_id、step_id、expires_at；`(user_id, logical_key)` 唯一。
- `quota_ledger`：user_id、bucket_id、reservation_id、action、units、balance_after、operator_id、reason、idempotency_key；不可变。
- `image_call_attempts`：user_id、tool、run_id、reservation_id、logical_unit、attempt、provider_request_id、send_state、output_asset_ids、error。

### 2.4 并发与事务

预占使用单条条件更新，禁止「先查余额再 Python 减法」：

```sql
UPDATE quota_buckets
SET reserved = reserved + :units
WHERE id = :bucket_id
  AND limit + adjustment - reserved - consumed >= :units
RETURNING id;
```

返回空行即 `QUOTA_EXHAUSTED`。日桶创建用 `INSERT ... ON CONFLICT DO NOTHING`。
结算/释放同样使用条件更新，保证 `reserved >= units`，不允许负余额。

### 2.5 接口

| 接口 | 说明 |
|---|---|
| `GET /api/me/entitlements` | 免费身份、日上限、已用、预占、可用、重置时间、规则版本、VIP coming_soon |
| `POST /api/quota/estimate` | 按工具与参数估算次数，不预占 |
| `GET /api/me/quota-ledger` | 本人额度流水分页 |
| `GET /api/admin/membership-policies` | 策略版本列表与当前生效项 |
| `POST /api/admin/membership-policies` | 发布新版本（默认明日生效） |
| `GET /api/admin/users/{id}/quota` | 指定用户当天额度与异常预占 |
| `POST /api/admin/users/{id}/quota-adjustments` | 有原因、可审计的额度调整 |

错误统一使用结构化 detail：

```json
{"detail": {"code": "QUOTA_EXHAUSTED", "message": "今日免费次数已用完，明日 00:00 重置",
  "available": 0, "required": 2, "reset_at": "2026-10-22T00:00:00+08:00"}}
```

前端 `api/client.ts` 同时兼容对象 detail 与旧的字符串 detail，逻辑判断只看 `code`。

## 3. Agent 流式与恢复域（A1/A2/A3）

### 3.1 轮次状态

`AgentRun` 新增独立 `phase`，避免复用 `queued` 表达待确认：

`planning / awaiting_confirmation / executing / completed / failed / canceled / needs_attention`

`status`（RunStatus）保留为兼容投影。新增字段：

- `idempotency_key`：用户级请求键，`(user_id, idempotency_key)` 唯一。
- `planning_attempt`：重新规划的尝试号，默认 1。
- `plan_draft`：公开草稿步骤（JSONB），只读展示，无执行权限。
- `public_summary`：可公开的阶段说明。
- `plan_version`：正式计划版本号。
- `checkpoint_thread_id`：图 thread，`turn:<turn_id>:<attempt>`。
- `last_event_seq`：轮次事件游标。

### 3.2 提交与规划

```
POST /api/sessions/{id}/messages {text, request_id}
→ 幂等检查，创建 AgentRun(phase=planning)
→ 写 planning.started 事件 + outbox
→ commit，返回 202 + turn
→ 队列 plan_turn(turn_id)
→ worker 流式规划，逐步写 plan_draft 事件
→ 完整工具调用经 validate() 后写正式计划，phase 变为 awaiting_confirmation / executing
→ 单步直接推进；多步等待确认
```

浏览器断开不取消任务；刷新通过 `GET /api/sessions/{id}/messages/{turn_id}` 与 SSE 快照恢复。
现有历史接口继续返回兼容的 `TurnOut`，前端先按新字段渲染。

### 3.3 事件

`agent_events`：`turn_id`、`seq`、`type`、`payload`、`created_at`；`(turn_id, seq)` 唯一。
事件类型：

- `turn.snapshot`
- `planning.started`
- `planning.summary.delta`（可选，正文为空不阻塞）
- `planning.step.draft`
- `plan.ready`
- `planning.failed`
- `step.updated`
- `turn.updated`

`GET /events/agent-runs/{turn_id}`：先订阅 Redis 再读快照，支持 `Last-Event-ID`/`after_seq` 补洞；Redis 只唤醒，缺口从 `agent_events` 读取。

规划流式实现：`ChatOpenAI.astream()` + `tool_call_chunks` 按 `index` 聚合。
草稿完整工具调用才允许进入正式计划；非法草稿从不创建 ToolRun。
模型不支持工具流式时降级为「开始规划 → 完整计划」两个真实事件。

### 3.4 图 checkpoint

- 状态只放可序列化字段：`turn_id / attempt / goal / context / runtime_version_id / plan / reply`。
- 模型客户端、DB session、事件 writer 不进入 state；节点内按 `turn_id` 从数据库重建依赖。
- worker 生命周期内创建 `AsyncPostgresSaver`，启动时 `setup()` 一次；关闭时关闭连接池。
- `thread_id = turn:<turn_id>:<attempt>`；规划异常恢复沿用同一 thread，用户主动重新规划才递增 attempt。
- checkpoint 只覆盖规划图，不宣称自动恢复图外图片执行。

### 3.5 步骤账本与恢复

- 新增 `AgentStep`：`(turn_id, step_id)` 唯一，保存顺序、参数、依赖、审批、状态、当前 ToolRun、输入/输出 revision。
- 新轮次以 `AgentStep` 为事实源，`AgentRun.plan` 仅作兼容投影；旧轮次先回填再切新调度。
- `ToolRun` 增加可空 `turn_id/step_id/attempt`。
- 恢复协调器在 worker 启动与周期扫描运行，租约 90 秒、扫描 30 秒、心跳 15 秒，均配置化。
- 恢复分类：计划已校验未写回 → 幂等写回；已有成功 ToolRun → 对齐终态；已建未投递 → 重投原 run_id；外部结果未知 → `needs_attention` 且不自动重发；待确认/已取消 → 保持原状。
- 画布应用以 `run_id` 唯一，资产产物 `(run_id, output_index)` 唯一；每步输出 revision 串联，旧 worker 租约不能覆盖新状态。
- 前置失败 → 下游 `blocked/skipped`，整轮允许结束为失败，不长期挂 running。

## 5. 影响面与回滚

- `tools.submit()`、`runs.create()` 是所有图片入口的公共路径，改动会影响生图、编辑工具、批量、Agent。采用「新增可选参数 + 默认行为不变」的渐进方式，分两步提交。
- `AgentRun.status` 语义保持不变，新 `phase` 只增不改；前端可按 phase 渲染，旧客户端仍能读 status。
- 新增表与可空字段，不做破坏性迁移；回退代码时新表可保留，已预占任务由兼容协调器继续结算。
- 额度开关 `QUOTA_ENFORCE`（默认开发关、生产开）决定是否真正拦截；关闭时仍记 shadow 预占与流水，便于核对调用链。
- 消息幂等键只在客户端提供时启用；旧客户端不传 `request_id` 时保持原行为。

### 已完成

**P1 额度闭环**

- 模型与迁移：`membership_policy_versions / quota_buckets / quota_reservations / quota_ledger / image_call_attempts`，种子免费策略每日 5 次。
- 服务：日桶条件更新预占、部分成功结算、失败释放、未知保留、管理员调整、流水、快照、估算。
- 工具计次：`ToolSpec.quota_units`；批量按「素材 × 操作链」展开，本地操作不计次。
- 事务：`runs.create(commit=False)` + `tools.submit` 原子创建任务与预占，提交后才投递；`execute` 成功结算、失败释放。
- 接口：`/api/me/entitlements`、`/api/quota/estimate`、`/api/me/quota-ledger`、管理员策略发布、用户额度查询与调整。
- 前端：侧栏免费会员额度卡、生图/批量/编辑工具/营销图/Agent 计划预估、用尽状态、VIP 即将开放、结构化错误 code、后台「会员权益」页。

**P2 轮次先落库与流式规划**

- `AgentRun` 增加 `phase / idempotency_key / planning_attempt / plan_draft / public_summary / plan_version / checkpoint_thread_id / last_event_seq`。
- `agent_events` 持久事件；seq 由行级条件自增，Redis 仅唤醒。
- `POST /messages` 异步规划开启时返回 202 + planning 轮次，worker 任务 `plan_turn` 流式写草稿；保留 `AGENT_ASYNC_PLANNING=false` 同步回退。
- `GET /messages/{turn_id}` 快照；`GET /events/agent-runs/{turn_id}` 轮次 SSE，先快照再补增量，支持 `after_seq` / `Last-Event-ID`。
- 前端订阅轮次事件、草稿卡、「取消规划」、刷新恢复；轮询降为 1.5 秒兜底。

**P3 规划图 checkpoint**

- `AgentState` 移出模型客户端，改为只含 `turn_id/goal/context/plan/reply`；运行时依赖用 ContextVar 注入。
- `AsyncPostgresSaver` 生命周期在 worker `on_startup/on_shutdown`；初始化失败时规划仍可用。
- 流式结果通过 `aupdate_state(as_node="plan")` 写入 checkpoint，再执行 verify；线程已有计划时直接续跑校验，不二次调用模型。

**P4 最小恢复闭环**

- `ToolRun` 增加 `turn_id/step_id/attempt`，Agent 步骤直接关联，不再只扫最近 20 轮。
- `AgentRun.planning_lease_until`：规划租约 300 秒；恢复扫描只捡过期租约，并用条件更新抢占，多实例安全。
- worker 每 30 秒执行 `recovery_tick`：重投过期 planning 轮次；重投超过 60 秒仍未开始的 queued ToolRun（沿用原 job id 去重）。
- `run_tool` 只领取 QUEUED 任务，RUNNING 状态不自动重跑。

## 9. 上线步骤与验收

- 前端构建：`frontend` 下 `npm run build:all`（如需发布版）。

### 9.3 手工验收

1. **额度**：新账号调用 `/api/me/entitlements` 看到免费会员与 5 次上限；连续生成直到 409，确认错误 detail 含 `code/available/required/reset_at`；裁剪/调色/投放尺寸不扣次数；生成 4 张成功 3 张只扣 3（可在额度流水核对 consume/release）。
2. **并发**：同时提交超过剩余次数的任务，只有额度内的任务创建成功，不出现负余额。
3. **流式规划**：发送「去背景再调亮」，POST 立即返回 planning；编辑页逐步出现草稿卡，随后替换为正式计划；刷新页面能恢复规划/待确认状态。
4. **幂等**：同一 `request_id` 重复提交只产生一轮；同键不同文本返回 409。
5. **恢复**：规划中杀掉 worker，300 秒后重启，过期 planning 轮次被重新投递；已排队但未开始的任务在扫描后继续执行。
6. **后台**：发布明天生效的新上限，当天次数不变；管理员调整必须填原因并出现在用户额度流水中。
7. **VIP 边界**：全站只出现「VIP 会员 · 即将开放」，无购买、充值、升级入口。

### 9.4 联调发现并已修复的问题（2026-10-21 本地实测）

| 问题 | 根因 | 处理 |
|---|---|---|
| 规划轮次永远停在「正在安排…」 | `services/agent.py` 用了 `sessions.load` 却没导入 `sessions` 模块，worker 直接 NameError | 补导入；`plan_turn` 读会话失败也要把轮次落到失败态 |
| 规划完成后 worker 报 `AttributeError: module 'app.agent' has no attribute 'spoken'` | `spoken` 只在 `app.agent.graph` 里，未从包导出 | `app/agent/__init__.py` 导出 `spoken`；服务层直接按函数导入 |
| 同步工具导致无限递归（RecursionError） | `ToolRun.turn_id` 关联后，`continue_plan` 在计划写回 `run_id` 之前就再次推进 | `continue_plan` 校验「计划里必须已登记该 run」；`_advance` 优先认领同 attempt 的已有任务 |
| worker 崩溃后轮次卡在 executing、输入框锁死 | 恢复扫描只处理 planning 轮次 | 恢复扫描新增「executing 且 60 秒无新事件」的轮次，重新推进；推进前抢租约 |
| 只有计划草稿卡、没有文字流 | 只消费了 tool_call_chunks，模型正文被丢弃；提示词还要求不要解释 | 提示词改为先说一句不超过 20 字的中文说明；新增 `planning.summary.delta` 事件，正文逐字下发，前端带光标渲染 |
| MiniMax 回复英文 | 提示词未强制语言 | 提示词补「无论用户用什么语言，一律用中文」 |
| Windows 下 checkpoint 初始化失败 | psycopg 异步连接不支持 ProactorEventLoop | worker 启动前切 `WindowsSelectorEventLoopPolicy`（Linux 无影响） |
| 额度数字不随预占刷新 | 只在提交消息时刷新额度 | 轮次事件 `plan.ready` / `turn.updated` 触发额度缓存失效 |
| 流式输出的一大段文字在结束时突然消失 | 结束时用 `spoken()` 把无计划的回复截成第一句（原本是为压掉模型讲内部参数） | 流式路径改为保留完整正文（`spoken(..., keep_full=True)`）；同步路径维持旧行为，并补回归测试 |
| 模型回复里的 Markdown 没渲染，`**` 直接露出来 | 对话区按纯文本渲染回复 | 新增 `components/ui/Markdown.tsx`（标题/列表/引用/粗斜体/行内代码/链接，全部走 React 文本节点，不解析 HTML），回复与流式正文都走它 |

### 9.5 本地实测记录
