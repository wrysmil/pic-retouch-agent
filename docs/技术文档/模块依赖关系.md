## 2. 总体分层

后端被切成五层，依赖方向自上而下单向，**不存在反向依赖**：

```
路由层 routers/          ← HTTP 边界，只做鉴权、参数解析、调用 service
   ↓
编排层 services/agent    ← 自然语言轮次的编排
执行外壳 services/tools  ← 唯一的工具执行入口（validate / submit / execute）
   ↓
注册表 app/tools/        ← 工具声明（ToolSpec），无业务实现
   ↓
模型层 models/ 事件层 events.py  队列 queue.py
```

关键点：**`app/agent/` 不是执行者**。它只产出「调哪个工具、传什么参数」，真正的校验与执行一律回到 `app/services/tools.py`。

### 3.3 四条关键依赖关系

**（1）`tools/__init__.py` 是收敛点。** `SPECS` 同时被三方消费：

- `agent/llm.py` 用 `convert_to_openai_function(spec.params.model_json_schema())` 生成模型的函数签名；
- `services/tools.py` 用 `spec.params.model_validate(params)` 做服务端校验；
- `schemas/agent.py` 的 `PlanStepOut.of` 调 `label_of` 填中文标签。

参数模型改一处，三处同时生效，不会漂移——这是本提交最重要的设计约束。

**（2）`agent/graph.py` → `services/tools.py` 是单向的。** 图内三个节点各调一个外壳函数：

| 节点 | 调用 | 说明 |
|---|---|---|
| `plan` | `llm.planner()` | 模型按 `SPECS` 产出 tool_calls |
| `verify` | `spec_of` + `tool_service.validate` | 模型输出默认不可信，先过校验；失败直接转成一句回复并短路到 `END` |
| `dispatch` | `tool_service.submit` | 校验通过才投递，拿到 `run_id` 回填给前端 |

`graph.py` 从不自己调 `handler`。

**（3）`services/tools.py` 是唯一执行入口。** 三条业务链路（自然语言、创作页生成、手工调用工具）在此合流，共用同一套状态流转与失败兜底：

```python
submit()  → runs.create() → (queued ? enqueue : execute())
execute() → runs.start() → spec.handler() → _record() → runs.finish()
```

`execute()` 用 `except (ProviderError, UnknownTool, ToolError)` 兜业务错误、裸 `except` 兜未预期异常并统一返回「执行失败，请重试」，不向外抛栈。

**（4）`tasks/tools.py` 复用同一个 `execute`。** 入队时以 `run.id` 作为 arq 任务 ID，消费前查 `run.status.is_terminal` 直接返回，保证队列重投和 worker 重启后不会二次扣费。原先特化的 `run_generate` 已删除。

由此可读出的三条结构特征：

- `MessageComposer` 是叶子组件，只依赖 `react`，不产生任何项目内依赖，便于独立复用。
- `AgentConversation` 是唯一同时依赖 `useAgent`（对话轮次）和 `useRun`（单次执行）的文件：步骤卡片用 `useTurns` 拿到的 `run_id` 交给 `useRun` 订阅 `/events/runs/:id` 的 SSE，终态后由 `useRun` 内部触发图片墙刷新。
- `api/agent.ts` 复用 `api/runs.ts` 的 `RunStatus`。后端 `AgentRun.status` 与 `ToolRun.status` 共用同一个枚举（`models/tool_run.py`），前端因此可以用同一套 `isTerminal` 判断两类记录的收敛。

## 6. 依赖约束（改动时须守住的约定）

1. **新工具只在 `app/tools/` 登记即可同时对界面与 Agent 生效**，不需要改 `graph.py`、`llm.py` 或 `schemas/agent.py`。
2. **handler 只返回业务结果**（`asset_ids` / `adopt_asset_id` / `document`），状态流转、失败兜底、产物入会话由 `services/tools.py` 统一负责。
3. **参数模型是校验的唯一来源**。新增字段必须写在 `ToolSpec.params` 指向的 Pydantic 模型里，不要在 handler 里另行解析。
4. **服务端填入的参数（如素材 ID、随机种子）放 `agent_hidden`**，不暴露给模型。
5. **`app/agent/` 不得直接 import `app/tools/canvas.py` / `retouch.py` 等具体工具模块**，只能经 `app.tools` 的 `SPECS` / `spec_of` / `label_of`。
6. **`services/tools.py` 不得 import `app.services.agent` 或 `app.agent`**，保持规划层与执行层解耦。

## 7. 数据模型关系

```
users ──┬── agent_runs.user_id
        ├── tool_runs.user_id
        └── edit_sessions.user_id

edit_sessions ──1:N── agent_runs.session_id      （本提交新增，CASCADE）
edit_sessions ──1:N── tool_runs.session_id        （本提交新增）
edit_sessions ──1:N── edit_history.session_id
edit_sessions ──N:M── assets  (session_assets)
```

`agent_runs.plan`(JSONB) 里的每一步带 `run_id`，指向该步产生的 `tool_runs`。因此：

- `AgentRun.status` 只表示**规划**是否成功；
- 每一步的**执行**进度由它自己的 `ToolRun` 承载，前端据此分别订阅 SSE。

`agent_runs.revision` 记录规划所基于的会话修订号，用于判断执行时画布是否已被改动。
