# 画布类工具

> 项目：pic-retouch-agent
> 主题：`app/tools/canvas.py` 的作用，以及它和画布文档、撤销历史的关系
> 对应提交：`34a76a9` feat: 确定性修图工具、线性撤销
> 日期：2026-09-28

## 0. 一句话概括

用户说「旋转 15 度」「裁成 1:1」，模型需要一个能调用的东西来完成它。`canvas.py` 就是这层适配器：把这类**只改数字、不碰像素**的操作包装成工具，让模型能像调用生图那样调用它们，同时完全不消耗算力。

配套阅读：模块依赖关系.md（讲整体分层，本文只讲画布这一支）。

## 1. 为什么需要它

工具分两大类，界线在 `_canvas()` 里那一行 `queued=False`：

| | 画布类工具（本文） | 像素类工具 |
|---|---|---|
| 代表 | 裁剪、翻转、缩放、旋转、透明度、图层顺序 | 生成图片、去背景、调色 |
| 改什么 | 一份 JSON 文档里的数字 | 真实的图像字节 |
| 耗时 | 毫秒级 | 秒到分钟级 |
| 执行方式 | 请求内当场完成 | 进队列，worker 异步跑 |
| 需要算力 | 不需要 | 需要 |

对模型来说这两者没有区别，都是「调一个工具」。但对系统来说必须分开——用户连点三次「旋转」应该立刻看到结果，而不是排队等三次生图。

## 2. 涉及四个文件

```
app/layers.py          画布文档长什么样（数据结构定义）
    ↓
app/edits/document.py  具体怎么改（纯函数，只改数字）
    ↑
app/tools/canvas.py    适配层：把模型的参数翻译成对上面纯函数的调用
    ↑
app/services/tools.py  执行外壳：校验、状态流转、落库、记撤销历史
```

依赖方向是单向的。**越下面的文件越不知道上面的存在**——`document.py` 不知道有模型存在，`canvas.py` 不知道有数据库存在。

## 3. 画布文档（LayerDocument）

### 3.1 它是描述，不是图像

真正的像素存在素材文件里。`LayerDocument` 只是用文字描述「画布多大、上面有哪些层、每层放在哪」。

`app/layers.py` 开头的注释说得很清楚：

> 画布文档结构。工具只修改此文档，像素合成由渲染环节按文档执行。

所以「翻转图层」在工具层只是把 `scale_x` 从 `1` 改成 `-1` 就结束了——**一个像素都没读**。真正重新合成图像是 `app/edits/render.py` 的事，只在需要出图时才做。

### 3.2 长什么样

```json
{
  "width": 1920, "height": 1080,
  "layers": [
    { "id": "base", "kind": "image", "name": "底图",
      "width": 1920, "height": 1080, "asset_id": "0000...001",
      "transform": { "x": 0, "y": 0, "scale_x": 1, "scale_y": 1, "rotation": 0 },
      "opacity": 1, "visible": true, "locked": true },
    { "id": "l2", "kind": "image", "name": "主体",
      "transform": { "x": 560, "y": 240, "scale_x": 1, "scale_y": 1, "rotation": 0 },
      "opacity": 1, "visible": true, "locked": false }
  ]
}
```

要点：

- **数组末尾 = 视觉上的最前面**。`resolve_layer` 里的 `reversed(document.layers)` 就是这个约定。
- **图层尺寸是素材的原始尺寸**，缩放不改变它。位置和大小都在 `transform` 里。
- **翻转靠负数表示**。`scale_x: -1` 就是水平翻转，没有单独的「翻转」字段。

### 3.3 图层 id 可以不传

所有工具的 `layer_id` 都是可选的。不传时 `resolve_layer` 自动挑最上层的可见图像层，所以用户说「旋转一下」不需要先指定哪一层。

## 4. 每个工具到底改了什么

以下是用真实模块跑出来的实际差异（初始文档：1920×1080，含底图 / 主体 / 文字三层）：

| 调用 | 文档变化 |
|---|---|
| `flip(None, 'horizontal')` | `[主体] scale_x: 1 → -1` |
| `set_opacity('l2', 0.4)` | `[主体] opacity: 1 → 0.4` |
| `scale('l2', factor=1.5)` | `[主体] scale_x: 1 → 1.5`，`scale_y: 1 → 1.5` |
| `scale('l2', scale_x=2.0)` | `[主体] scale_x: 1 → 2.0`（只动 X） |
| `rotate('l2', angle=15)` | `[主体] rotation: 0 → 15` |
| `reorder('l2', 'top')` | 层序 `['base','l2','l3'] → ['base','l3','l2']`，transform 不变 |
| `crop(ratio=1:1)` | 画布 `1920×1080 → 1080×1080`，所有图层 `x` 减 420 |
| `crop(rect=(0,0,0.5,1))` | 画布 `1920×1080 → 960×1080`，图层坐标不变 |

两个容易忽略的点：

- **裁剪是唯一改画布尺寸的工具**。裁掉左侧 420 像素后，每个图层的 `x` 都减 420，让内容跟着画布走；图层自身的 `width`/`height` 不变，因为那描述的是素材，不是画布。
- **图层重排只动列表顺序**，不碰任何坐标和 transform。

## 5. 深拷贝：撤销功能的地基

`document.py` 里六个函数，**第一行都是 `model_copy(deep=True)`**，无一例外：

```python
def scale(document, layer_id, *, factor=None, ...):
    doc = document.model_copy(deep=True)      # 拷贝一份
    transform = resolve_layer(doc, layer_id).transform
    transform.scale_x *= factor               # 在副本上改
    return doc                                 # 返回副本
```

传进来的对象从头到尾没被碰过。理解成「拿原件去复印，在复印件上改，改完把复印件交出去」即可。

这带来两个好处：

1. **撤销有了数据基础。** 旧版本和新版本是两个互不干扰的对象，历史栈只要分别存起来就行。
2. **函数是纯的。** 可以脱离数据库单测，不需要起服务。

注意 `deep=True` 不能省。浅拷贝只复制最外层的 `LayerDocument`，内部的 `layers` 列表和每个 `Layer` 还是同一批对象，改一个图层的 transform 就会污染原文档。

**唯一的例外**：`crop` 是「先算好、校验通过，再拷贝」——裁剪框太小时直接抛 `EditError`，不会浪费一次深拷贝。

## 6. 撤销是怎么实现的

### 6.1 存的是快照，不是操作日志

每次编辑，`apply_edit` 会在改动前拍一张快照：

```python
before = snapshot(record)     # { document, current_asset_id, revision }
# ... 改当前状态 ...
_append_history(..., params={**params, "before": before},
                      result={**result, "document": record.document, ...})
```

也就是说，**每条历史记录里存了改动前后两份完整文档**，都在 `edit_history` 表的 JSONB 字段里。

### 6.2 撤销只是赋值

因为存的是完整快照，回退不需要重跑任何业务代码：

```python
def _restore(record, state):
    record.document = state["document"]
    record.current_asset_id = uuid.UUID(state["current_asset_id"])
    record.revision = state["revision"]
```

```python
undo()  →  _restore(record, before)          →  history_seq -= 1
redo()  →  _restore(record, entry.result)    →  history_seq += 1
```

代价是空间（每次编辑存两份文档），换来的是可靠：连「生成图片」这种昂贵且不可逆的操作都能撤销，因为素材早就落库了，历史里记着该切回哪张。

### 6.3 是线性的，不支持分支

`edit_history.py` 里写得很清楚：「线性编辑记录，只保留最近 20 条，不提供版本树与分支」。对应两个行为：

- **只留 20 条**，超出的旧记录会被删掉。
- **撤销后再做新操作，重做分支会被删掉**——和 Photoshop 里「新操作清空重做栈」一致。

## 7. 完整调用链

```
用户/模型请求「旋转 15 度」
   ↓
services/tools.py  validate()      ← 按 ScaleIn 校验参数，转成 dict 存进 ToolRun
   ↓
services/tools.py  submit()        ← queued=False，当场执行，不入队
   ↓
services/tools.py  execute()
   ↓
canvas.py  _apply()
   │   ├─ require_session()          取当前编辑会话
   │   ├─ document_of(record)        JSON dict → LayerDocument 对象
   │   ├─ mutate(doc, params)        ← 调 document.scale()，返回新对象
   │   └─ 翻译异常                    LayerMissing / EditError → ToolError
   ↓
   返回 {"document": {...}}          ← 只交结果，不落库
   ↓
services/tools.py  _record()
   ↓
sessions.py  apply_edit()           ← 存快照、改画布状态、写历史、推 SSE
   ↓
services/tools.py  runs.finish()    ← 标记成功/失败
```

**注意 `_apply` 到返回就结束了。** 它不认识 `apply_edit`，也不认识「撤销」这个概念——`canvas.py` 里搜不到 `apply_edit`、`sessions`、`history_seq` 任何一个词。

它和落库之间只靠一个约定：**返回值的 key 叫 `document`**。`_record` 认这个 key：

```python
raw_document = result.get("document")
if document is not None or current is not None:
    await sessions.apply_edit(...)
else:
    await sessions.record_result(...)     # 只产出素材的走这条
```

像素类工具返回的是 `{"asset_ids": [...], "adopt_asset_id": "..."}`，于是走另一个分支。**同一个函数按返回值自动分流**——工具只管产出，中间件负责记账。

## 8. 参数怎么从模型传到业务代码

同一份定义同时喂给三个地方，这是这套设计最重要的约束：

```
RotateIn（参数模型）
   ├─→ agent/llm.py      转成 JSON Schema，模型据此生成参数
   ├─→ services/tools.py model_validate() 校验并转成 dict 存进 ToolRun
   └─→ canvas.py         handler 拿到 dict，取值传给 document.py
```

以 `RotateIn` 为例：

```python
class RotateIn(LayerRef):          # 继承得到可选的 layer_id
    angle: float = Field(default=None, ge=-360, le=360)
    rotation: float = Field(default=None, ge=-360, le=360)

    @model_validator(mode="after")
    def _need_angle(self):          # 跨字段规则：至少给一个角度
```

三点值得留意：

- **`Field(...)` 出现在默认值位置，但它不是默认值**，而是一份校验配置。没写 `default=` 就是必填。
- **`Field` 管单字段范围，`model_validator` 管跨字段规则**。`ge/le` 是闭区间，`gt/lt` 是开区间——选哪个取决于「端点值有没有意义」，比如 `width` 用 `gt=0`（宽 0 无意义）而 `le=1`（裁满整幅可以）。
- **`agent_hidden` 会把 `layer_id` 从给模型的 schema 里删掉**（`agent/llm.py`），因为图层 id 由服务端从会话上下文判断，不该让模型填。

两套角度字段并存（`angle` 增量 / `rotation` 绝对值，两组缩放同理）是为了容忍模型的不同表述，再由校验器兜住「一个都不给」的情况。

## 9. 新增一个画布工具

需要写的东西很少：

```python
# 1. 入参模型：需要图层 id 就继承 LayerRef
class DesaturateIn(LayerRef):
    amount: float = Field(ge=0, le=1)

# 2. 在 document.py 写纯函数，第一行深拷贝
def desaturate(document, layer_id, amount):
    doc = document.model_copy(deep=True)
    resolve_layer(doc, layer_id).opacity *= 1 - amount
    return doc

# 3. handler：两行
async def desaturate_layer(session, run) -> dict:
    return await _apply(
        session, run, lambda doc, p: desaturate(doc, p.get(_LAYER), p["amount"])
    )

# 4. 注册
DESATURATE_LAYER = _canvas("desaturate_layer", "去饱和", "……", DesaturateIn, desaturate_layer)
```

不用写落库、状态流转、撤销历史、异常兜底——这些分别在 `_record`、`execute`、`apply_edit`、`ToolError` 里，已经统一处理好了。

`_canvas()` 还顺手补齐了默认值：同步执行、必须绑定会话、隐藏 `layer_id`。

**约束**（与《模块依赖关系》第 6 节一致）：

1. 新工具只在 `app/tools/` 登记，不改 `graph.py`、`llm.py`。
2. handler 只返回业务结果，不碰状态流转。
3. 参数校验只写在参数模型里，不在 handler 里另行解析。
4. `document.py` 保持纯函数，不 import 任何数据库或工具相关模块。
