# 部署文档（阿里云 2核4G 单机 · 先 IP 后域名）

> 适用场景：面试演示 / 低并发自用。先只用公网 IP 访问，域名和 HTTPS 后续再加（见文末第 9 节）。
> 全部服务用 Docker Compose 部署在一台 2核4G 的阿里云 ECS 上，资源不够时再按第 10 节拆到第二台服务器。

## 1. 部署架构

```
                        公网
                          │
          ┌───────────────┴───────────────┐
          │       2核4G ECS（本机）        │
          │  ┌─────────────────────────┐  │
   :7302 ─┼─▶│ app   （API + 前端页面） │  │
          │  └─────────────────────────┘  │
          │  ┌─────────────────────────┐  │
          │  │ worker（图像处理任务）   │  │
          │  └─────────────────────────┘  │
 :7313 ───┼─▶│ minio （签名图片直链）   │  │
          │  │ postgres · redis（内网） │  │
          │  └─────────────────────────┘  │
          └───────────────────────────────┘
```

5 个容器，全部由仓库根目录的 `docker-compose.yml` 定义：

| 服务 | 作用 | 端口 | 是否公网开放 |
| --- | --- | --- | --- |
| app | FastAPI 接口 + 工作台前端静态页 | 7302 | ✅ 开放 |
| minio | 对象存储，浏览器通过签名 URL 取图 | 7313（API）/ 7314（控制台） | ✅ 仅 7313；7314 不开放 |
| worker | arq 任务进程，跑抠图/拆层/超分等 | 无 | ❌ |
| postgres | 数据库 | 7311 | ❌ |
| redis | 队列与缓存 | 7312 | ❌ |

**2核4G 能跑 Docker 吗？** 能。Docker 本身只占 ~150M 内存，整套容器空闲约 1.3-1.5G，图像任务峰值约 2.5G，4G 内存足够（配合第 2.3 节的 swap 兜底）。CPU 2 核在低并发下够用，任务多时会排队，属于预期行为。

## 2. 服务器准备

### 2.1 安装 Docker

Alibaba Cloud Linux 3：

```bash
sudo dnf config-manager --add-repo https://mirrors.aliyun.com/docker-ce/linux/centos/docker-ce.repo
sudo dnf install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
```

Ubuntu 22.04 / 24.04：

```bash
curl -fsSL https://get.docker.com | sudo bash
```

装好后启动并让当前用户免 sudo：

```bash
sudo systemctl enable --now docker
sudo usermod -aG docker $USER   # 重新登录后生效
docker --version && docker compose version   # 验证
```

> 如果 `docker pull` 很慢：登录阿里云容器镜像服务控制台，在「镜像工具 → 镜像加速器」拿专属地址，写入 `/etc/docker/daemon.json` 的 `registry-mirrors` 后 `sudo systemctl restart docker`。

### 2.2 拉取代码

```bash
sudo dnf install -y git   # 或 apt install git
git clone https://github.com/wrysmil/pic-retouch-agent.git
cd pic-retouch-agent
```

### 2.3 添加 2G swap（强烈建议）

worker 跑大图时内存会冲高，swap 是防 OOM 的保险：

```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
free -h   # 确认 Swap 一行出现 2.0Gi
```

## 3. 阿里云安全组：开放哪些端口

控制台 → ECS 实例 → 安全组 → 入方向 → 手动添加。IP 直访阶段只需三条：

| 端口 | 协议 | 授权对象 | 用途 |
| --- | --- | --- | --- |
| 22 | TCP | 你的本机公网 IP（最安全） | SSH 登录 |
| 7302 | TCP | 0.0.0.0/0 | 工作台页面 + API |
| 7313 | TCP | 0.0.0.0/0 | MinIO 签名图片直链（浏览器要用） |

不开放的端口（安全组默认拒绝入方向即可）：7311（数据库）、7312（Redis）、7314（MinIO 控制台）。域名阶段再开 80/443。

> 7313 公网可达意味着 MinIO 的账号密码就是唯一防线，所以第 4.2 节务必修改默认密码，不要沿用 `retouch_dev`。

## 4. 配置

### 4.1 生成 .env

```bash
cp .env.example .env
```

需要修改/补齐的项：

| 变量 | 怎么填 |
| --- | --- |
| `APP_ENV` | **IP 阶段保持 `development`**（见下方说明） |
| `JWT_SECRET` | `openssl rand -hex 32` 的输出 |
| `SECRET_ENC_KEY` | Fernet 密钥，见下方生成命令（不设则后台无法保存厂商密钥） |
| `S3_PUBLIC_ENDPOINT` | 先留空，稍后在 compose 里改（见 4.2） |
| `ALLOWED_PROVIDER_HOSTS` | 保持默认即可（含 toookens / minimax / openai / dashscope） |
| `TOOOKENS_API_KEY` | 若要接 Toookens 生图，填真实 Key |
| `MINIMAX_API_KEY` | 若要接 MiniMax 文本，填真实 Key |

> **为什么 IP 阶段不能设 `APP_ENV=production`**：代码里登录 Cookie 在 production 下会带 `Secure` 标记（`backend/app/routers/auth.py:29`），纯 HTTP 访问时浏览器不会回传 Cookie，表现就是「登录成功但立刻掉登录」。等域名 + HTTPS 就绪后再切 `production`。

`SECRET_ENC_KEY` 生成方式（镜像构建完成后用容器生成，或本机装过 cryptography 就用 python）：

```bash
docker compose --profile deploy run --rm --no-deps app \
  python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

把输出的一行贴到 `.env` 的 `SECRET_ENC_KEY=` 后面。

### 4.2 修改 docker-compose.yml（两处必改）

compose 的 `environment:` 会覆盖 `.env`，所以下面两处必须直接改 compose 文件：

1. **app 服务的 `S3_PUBLIC_ENDPOINT`**（当前是 `http://localhost:7313`，不改的话浏览器会去访问用户自己的电脑，图片全部裂图）：

   ```yaml
   S3_PUBLIC_ENDPOINT: http://<你的公网IP>:7313
   ```

2. **MinIO 默认密码**（7313 对公网开放，默认的 `retouch/retouch_dev` 必须换）：

   ```yaml
   environment:
     MINIO_ROOT_USER: retouch
     MINIO_ROOT_PASSWORD: <换成一个强密码>
   ```

   同时在 `.env` 里同步 `S3_SECRET_KEY=<同一个强密码>`（`S3_ACCESS_KEY` 与 `MINIO_ROOT_USER` 保持一致）。

### 4.3 建议：限制 worker 并发

编辑 `backend/app/worker.py`，把 `max_jobs = 4` 改为 `max_jobs = 2`。2 核 CPU 下 4 个图像任务并发只会互相拖慢并放大内存峰值。

### 4.4 建议：中间件端口只绑本机

`docker-compose.yml` 里 postgres / redis / minio 的 `ports` 目前绑定在 `0.0.0.0`，安全组虽然挡住了公网，但再加一层本机绑定更稳妥：

```yaml
ports:
  - "127.0.0.1:7311:5432"   # postgres
  - "127.0.0.1:7312:6379"   # redis
  - "127.0.0.1:7313:9000"   # minio API —— 注意：这一条不能绑 127.0.0.1！
  - "127.0.0.1:7314:9001"   # minio console
```

> **例外**：MinIO 的 7313 是浏览器直连的，必须保持 `0.0.0.0` 绑定；只把 7311 / 7312 / 7314 收窄。等域名阶段用 nginx 反代后，7313 也可以收窄。

## 5. 一键部署

配置完成后，依次执行 4 条命令（第 1 条包含镜像构建，2核4G 上约 10-20 分钟）：

```bash
# 1) 构建并启动全部 5 个容器
docker compose --profile deploy up -d --build

# 2) 初始化数据库表
docker compose --profile deploy exec app alembic upgrade head

# 3) 创建管理员账号（工作台登录用）
docker compose --profile deploy exec app python scripts/init_admin.py create admin '<设置一个强密码>'

# 4) 查看状态：5 个容器都应 Up，postgres/redis/minio 显示 healthy
docker compose --profile deploy ps
```

就这四步，"一键部署"成立；第 2、3 步单独执行是因为迁移和管理员初始化是幂等的一次性操作，不应该每次启动都跑。

首次 `up` 会拉取 postgres / redis / minio / node / python 等基础镜像（约 2-3G 磁盘），构建会用 `uv sync` 装 Python 依赖（含 rembg/onnxruntime，约 300M+），请保证系统盘 ≥ 40G。

## 6. 首次配置模型（登记厂商与模型）

> **当前镜像只打包了工作台前端，不含管理后台前端**（`Dockerfile` 只复制了 `frontend/dist`，管理后台 `dist-admin` 是独立构建）。IP 阶段用命令行脚本完成登记，域名阶段可以用 nginx 托管后台页面（见第 9 节）。

在工作台能用之前，至少要发布一个"文本模型 + 生图模型"的运行版本。以 Toookens 生图 + MiniMax 文本为例（Key 已在 `.env` 填好）：

```bash
# 登记生图连接与模型（不产生调用费用）
docker compose --profile deploy exec app python scripts/register_toookens.py

# 登记文本模型，并发布运行版本
docker compose --profile deploy exec app python scripts/register_minimax.py --image-model-slug qwen-image-3.0

# 连通性自检
docker compose --profile deploy exec app python scripts/check_providers.py
```

之后在后台「启用/停用模型」就是热更新开关（无需重启容器）。

## 7. 验证

```bash
# 健康检查：应返回 api/database/storage 均 ok
curl http://<公网IP>:7302/api/health
```

浏览器打开 `http://<公网IP>:7302`：

1. 用第 5 步创建的管理员账号登录
2. 上传一张图，输入一句修图指令（如"把背景换成纯白"），提交
3. 任务从「排队中」变为完成，结果图正常显示 → 全链路 OK
4. 如果结果图裂图：检查浏览器控制台图片地址是否为 `<公网IP>:7313/...`（不是 localhost），以及安全组 7313 是否放行

## 8. 日常运维

```bash
# 更新部署（拉新代码后）
git pull
docker compose --profile deploy up -d --build
docker compose --profile deploy exec app alembic upgrade head

# 看日志
docker compose --profile deploy logs -f app worker

# 重启单个服务
docker compose --profile deploy restart app

# 备份数据库
docker compose --profile deploy exec postgres pg_dump -U retouch retouch > backup-$(date +%F).sql

# 备份 MinIO（对象数据在 volume minio_data，可用容器内 mc 同步到目录）
docker compose --profile deploy exec minio mc mirror /data /tmp/minio-backup
```

## 9. 后续：绑定域名 + HTTPS

1. DNS 添加 A 记录：`你的域名 → ECS 公网 IP`（几分钟生效）
2. 安全组追加放行 80 / 443
3. 服务器上装 nginx，反代 app 与 MinIO（MinIO 用子域，保持签名 URL 的 Host 一致）：

   ```nginx
   server {
       listen 80;
       server_name your-domain.com;
       location / {
           proxy_pass http://127.0.0.1:7302;
           proxy_set_header Host $host;
           proxy_set_header X-Forwarded-Proto $scheme;
       }
       # SSE 事件流：关闭缓冲
       location /events {
           proxy_pass http://127.0.0.1:7302;
           proxy_buffering off;
           proxy_read_timeout 3600s;
           proxy_set_header Host $host;
       }
   }

   server {
       listen 80;
       server_name s3.your-domain.com;   # 专门给 MinIO
       location / {
           proxy_pass http://127.0.0.1:7313;
           proxy_set_header Host $host;
       }
   }
   ```

4. certbot 签 HTTPS 证书（`sudo certbot --nginx`），然后把：
   - `docker-compose.yml` 的 `S3_PUBLIC_ENDPOINT` 改为 `https://s3.your-domain.com`
   - `.env` 的 `APP_ENV` 改为 `production`（此时 HTTPS 就绪，Secure Cookie 不会出问题）
   - 重新 `docker compose --profile deploy up -d`
   - 安全组关掉 7302 / 7313 的公网入方向（全部走 nginx）
5. 管理后台页面：在任意有 Node 22 的机器上 `npm run build:admin` 出 `frontend/dist-admin`，拷贝到服务器，用 nginx 单独一个 server_name 托管并反代 `/api` 到 7302。

## 10. 以后资源不够时：拆分到第二台服务器

按「公网计算层 / 私网数据层」拆（4G 那台保持域名入口）：

| 机器 | 跑什么 |
| --- | --- |
| 2核4G（公网，域名） | nginx + app + worker |
| 2核2G（纯内网） | postgres + redis + minio |

要点：两台必须同地域同 VPC；2G 机器安全组只放行 4G 机器的内网 IP 访问 5432/6379/9000；4G 机器上 `DATABASE_URL` / `REDIS_URL` / `S3_ENDPOINT` 指向 2G 内网 IP；`S3_PUBLIC_ENDPOINT` 仍是公网子域（由 4G 的 nginx 反代到 2G 的 MinIO）；两台 `.env` 的 `JWT_SECRET` / `SECRET_ENC_KEY` 必须一致。compose 拆成两份（一份中间件、一份 app+worker）。

## 11. 常见问题

| 现象 | 原因与处理 |
| --- | --- |
| 登录成功但马上掉登录 | `APP_ENV=production` +  HTTP 访问；改回 `development`，或先上 HTTPS |
| 结果图裂图 / 一直转圈 | `S3_PUBLIC_ENDPOINT` 没改成公网 IP，或安全组没开 7313 |
| 任务一直「排队中」 | worker 没起来：`docker compose --profile deploy ps` 查看，`logs worker` 找报错 |
| 构建到最后 OOM | swap 没开或太小；或改到本地构建：`docker buildx build --platform linux/amd64 -t <仓库>/pic-retouch:latest .` 后推送镜像到阿里云 ACR，服务器只 `docker compose pull` |
| 容器反复重启 | `docker compose --profile deploy logs <服务名>`；MinIO 若崩溃循环，确认镜像版本是 latest（旧版读不了新版数据卷格式，compose 注释有说明） |
| 磁盘变满 | `docker system df` 查看；`docker image prune` 清理旧镜像（不要 `-a`，会删掉正在用的） |
| 服务器卡顿、swap 用满 | 大图任务太多：调低 `max_jobs`，或按第 10 节把 worker 迁到 2G 机器 |
